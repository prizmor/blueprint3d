# Руководство разработчика

[English version](development.en.md) · [Карта документации](README.ru.md)

Как работать над самим Blueprint3D: подготовка, правила, как расширять каждую часть, тестирование, документация, версии. Как пользоваться инструментом — в [руководстве](manual.ru.md); как он устроен — в [архитектуре](architecture.ru.md) и [справочнике модулей](modules.ru.md).

## Подготовка

1. `git lfs install`, клонировать, запустить `scripts/install.ps1` (Windows) или `scripts/install.sh`.
2. Blender 5.3 (для build, render, posetest, одежды) и Edge/Chrome/Chromium (для PNG/PDF).
3. `PYTHONPATH=<repo>` и `venv/…/python -m bp3d selftest --draw` должны проходить до любых изменений — иначе свою поломку не отличить от уже существующей.

Шага упаковки нет: пакет запускается из дерева исходников через `PYTHONPATH`.

## Правила

### Совместимость

- **Существующие спецификации продолжают работать.** Новые параметры — именованные аргументы со значениями по умолчанию, которые воспроизводят старое поведение. Переименование или удаление публичной функции, поля `Model.add`, ключа листа или параметра CLI — ломающее изменение: избегайте его; если без него никак, оставьте псевдоним хотя бы на одну минорную версию и пометьте запись в CHANGELOG **[breaking]**.
- **Хеши апрува.** `spec_hash` включает `kit.py`, `mesh.py`, а для одежды — `body.py`, `garment.py`, `rig.py` и файл тела. Любая правка этих файлов — даже комментария — делает устаревшими все апрувы пользователей. Группируйте такие правки, сообщайте о них в pull request, помечайте запись в CHANGELOG **[hash]**. Изменения, не влияющие на геометрию, вносите в другие файлы (`drawing.py`, `build.py`, `bl_*.py`, `__main__.py` не хешируются).
- **Тела.** Пересборка `bodies/*` делает недействительными апрувы одежды. Тела сохраняйте только через `bl_common.save_clean()`.

### Код

- Python 3.10–3.13; зависимости только из `requirements.txt` (build123d, numpy, scipy). Новой зависимости нужно обоснование в pull request и строка в `requirements.txt` с закреплённой или ограниченной версией.
- Скрипты Blender (`bl_*.py`) выполняются во встроенном Python Blender: только `bpy`, `mathutils`, numpy — без build123d и scipy. Со стороной Python они общаются через файлы (`manifest.json`, `.npz`, `.glb`, JSON) и в конце печатают маркер `BP3D_DONE` (см. [архитектуру](architecture.ru.md#модель-процессов)).
- Узлы шейдеров ищите по типу, никогда по имени (имена локализуются); идентификаторы перечислений читайте, а не вписывайте в код.
- Единицы: миллиметры в спецификациях, листах и отчётах; метры только внутри Blender и в экспортированных файлах. Оси — см. [архитектуру](architecture.ru.md#системы-координат).
- Комментарии и сообщения CLI — на русском (сложившееся соглашение); docstring объясняет *зачем*, а не *что*. Комментарии на английском от участников принимаются.
- Делайте функции чистыми, где возможно: функции геометрии принимают сетки/пути и возвращают новые объекты; никакого скрытого состояния модуля. Существующее глобальное состояние перечислено в [справочнике модулей](modules.ru.md#глобальное-состояние) — нового не добавляйте.
- Никаких абсолютных путей, имён пользователей, названий студий и проектов в коде, документации и поставляемых файлах.

### Коммиты и pull request

- Одна тема на pull request. Ветка от `main`; `main` защищена — сливает только мейнтейнер, после ревью и зелёного CI.
- Сообщения коммитов: в первой строке `Область: что изменилось` (`Garment: ...`, `Drawing: ...`, `CI: ...`), причина — в теле.
- Только squash merge; заголовок PR становится заголовком коммита.

## Правила документации

**Документация — часть изменения, а не доделка потом.** Pull request, меняющий поведение инструмента, закончен только тогда, когда документация описывает новое поведение.

| Вы изменили | Обновить |
|---|---|
| Любое поведение, параметр, значение по умолчанию, вывод | `CHANGELOG.md` в разделе **Unreleased** — всегда |
| Команду, флаг, код выхода, переменную окружения | [`cli`](cli.ru.md) |
| Файл, который инструмент читает или пишет, ключ JSON, структуру папок | [`file-formats`](file-formats.ru.md) |
| Ответственность модуля, публичную функцию, структуру данных | [`modules`](modules.ru.md) |
| Поток данных, новую границу процессов, новый этап | [`architecture`](architecture.ru.md) |
| API спецификации, видимый пользователям (функции kit/mesh, поля `Model.add`, блоки одежды, ключи листа), правило, выведенное на практике, ограничение | [`manual`](manual.ru.md) |
| Как участвовать, тестировать, выпускать релизы | этот файл, [`CONTRIBUTING.md`](../CONTRIBUTING.md), [`AGENTS.md`](../AGENTS.md) |
| Установку, требования | [`README.ru.md`](../README.ru.md), [`manual`](manual.ru.md#установка), `scripts/` |

- **Оба языка.** Каждый документ существует в виде `*.en.md` и `*.ru.md` с одинаковым содержанием. Обновляйте оба в одном pull request; если можете написать только один, скажите об этом в pull request, и мейнтейнер допишет второй до слияния.
- **Факты из кода.** Имена, значения по умолчанию, ключи и пороги копируются из кода с указанием модуля, где они находятся. Не описывайте намерения как поведение.
- **Новые приёмы — в образцы.** Новый способ что-то построить получает образец в `examples/` или раздел в стартовом шаблоне, чтобы `selftest` поддерживал его рабочим.
- **CI проверяет минимум.** Задача `docs` роняет pull request, который меняет `bp3d/`, `scripts/`, `examples/`, `bodies/` или `requirements.txt` без изменения `CHANGELOG.md` и без изменения хотя бы одного файла документации. Мейнтейнер может поставить метку `docs-not-needed` на изменения без видимого эффекта (чистый рефакторинг); запись в CHANGELOG всё равно обязательна.
- **Ревью проверяет документацию.** Мейнтейнер читает дифф документации так же внимательно, как дифф кода; pull request, документация которого расходится с кодом, не сливается.

## Расширение инструмента

### Новая команда CLI
1. `cmd_<name>(obj, args)` в `bp3d/__main__.py`; подпарсер в `main()`; запись в диспетчере.
2. Вывод в `<object>/out/<name>/`; в любой записываемый отчёт заносите `spec_hash`.
3. Код выхода 1 для сбоев, которые должен заметить скрипт.
4. Документация: [cli](cli.ru.md), [file-formats](file-formats.ru.md), если команда пишет файлы, таблица команд в руководстве.

### Функция геометрии (`kit.py`) или построитель квадов (`mesh.py`)
1. Чистая функция, миллиметры, сетки `(nu, nv, 3)`, внешняя нормаль `du × dv`.
2. Построитель квадов возвращает `QuadMesh`, который проходит `check` (замкнутый, манифолдный, согласованный порядок обхода, соотношение сторон ≤ 8).
3. Используйте её в образце, чтобы её покрывал `selftest`.
4. **[hash]** в CHANGELOG. Документация: руководство (Геометрия), [modules](modules.ru.md).

### Отделка
`model.FINISHES` (значение серого, металличность, шероховатость для серой модели), соответствующий материал в `bl_render.py` (презентация) и таблица тун-шейдинга в `bl_pose.py` (одежда). Документация: руководство (Спецификация объекта).

### Ключ листа
Читайте его в `drawing.build_body` со значением по умолчанию, при котором старые листы не меняются. Документация: руководство (Лист), [modules](modules.ru.md#drawingpy).

### Блок одежды
Метод `garment.Outfit` по образцу соседних: сетка сверху вниз, нормаль наружу, `push_out` от тела, именованные края в `Piece.edges` для блоков, которые к нему крепятся. Проверка — `check` (зазор, петли суставов) и `posetest`. Используйте его в `examples/garment_basic` или в новом образце одежды. **[hash]**. Документация: руководство (Одежда → Блоки одежды), [modules](modules.ru.md#garmentpy).

### Возможность на стороне Blender
Правьте скрипт `bl_*.py`; новые данные передавайте через манифест или `.npz` (добавляйте ключи, никогда не меняйте существующие); добавляйте новые ключи отчёта, а не переименовывайте старые. Документация: [file-formats](file-formats.ru.md).

### Новое тело
Любой `.blend`/`.glb`/`.fbx` с одной арматурой и мешем с весами; тело стоит на полу, лицом к −Y в Blender. Роли костей угадываются по именам; для необычных имён нужен `roles=`. Поставляемые тела: происхождение и лицензия — в `bodies/README.md`; должны быть совместимы с CC0; сохраняются через `save_clean()`.

## Тестирование

| Уровень | Что | Когда |
|---|---|---|
| `python -m bp3d selftest` | `check` каждого образца; `posetest --no-render` образцов одежды | после каждого изменения в `bp3d/` |
| `selftest --draw` | + `draw --quick` каждого образца (нужен браузер) | перед pull request; посмотрите листы в `examples/*/out/drawing/` |
| `build` / `render` / `posetest` на затронутом образце | этап Blender | после изменений в 3D, скриптах Blender, одежде |
| CI `selftest` | образцы жёстких предметов на Ubuntu без Blender | каждый pull request и push в `main` |
| CI `docs` | правила документации | каждый pull request |

`selftest` — набор регрессионных тестов: образец, переставший проходить, — это регрессия, а не образец на удаление. Исправление ошибки приходит вместе с образцом (или изменением образца), который поймал бы её, когда это осуществимо.

## Версии и релизы

- [Семантическое версионирование](https://semver.org/): **major** — ломающее изменение API спецификации или формата файлов; **minor** — новые возможности, изменения, меняющие хеши апрува; **patch** — исправления без изменения хешей и API.
- Версия хранится в `bp3d/__init__.py` (`__version__`) и записывается в `approved.json`.
- Релиз: перенести записи **Unreleased** в `CHANGELOG.md` под заголовок новой версии с датой, увеличить `__version__`, слить, поставить тег `vX.Y.Z` на `main`, создать GitHub release с разделом CHANGELOG.
